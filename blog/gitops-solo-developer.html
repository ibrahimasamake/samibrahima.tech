How I ship 20 apps alone with Jenkins and Argo CD

I run Sougba, a marketplace with more than ten services, a web app, a mobile app and a back office — and I am the only engineer. The thing that keeps this possible is a deploy pipeline so boring that I almost never think about it. Here is how it works, what broke, and what I would change.

The rule: git is the only way into production

Nobody, including me, runs kubectl apply against production by hand. Every change reaches the cluster through a commit. That one rule gives me three things for free: a history of every deploy, a review point before it happens, and a rollback that is just git revert.

The pipeline in four steps

  1. Pull request. A change goes to the service repo as a pull request. A GitHub Actions check runs the same build and tests that the real pipeline will run. If it is red, it does not merge.
  2. Build. Jenkins watches the main branch of every service. When a new commit lands, it builds a Docker image and pushes it to a private registry, tagged with the build number — never just latest, so every running version can be traced back to a build.
  3. Record. Each service has a second repository, its deploy repo, that holds only Kubernetes manifests (Kustomize, with a prod overlay). Jenkins clones it, bumps the image tag, and pushes. That commit is the deploy.
  4. Sync. Argo CD watches all deploy repos through one parent "app of apps". It sees the new tag and rolls the Deployment. Readiness probes and a short minReadySeconds make sure a broken pod never takes traffic.

About 20 applications follow this exact path. Adding a new service means copying a Jenkinsfile, a Dockerfile and a deploy repo template — about fifteen minutes of work.

Why two repos per service?

It feels like overhead at first. It pays for itself the first time something goes wrong:

  • The service repo answers "what does the code do?". The deploy repo answers "what is running right now?". When production misbehaves at night, I only need the second question.
  • Rolling back never needs a rebuild. I revert one line in the deploy repo and Argo CD puts the previous image back in under a minute.
  • Configuration changes (replicas, memory limits, probes) are deploys too, with the same history and the same rollback.

What broke, and what I learned

  • A pipeline that silently stops is worse than one that fails. Once, the machine that runs Jenkins had its Docker daemon stopped. Nothing failed — nothing ran. Commits piled up on main and I believed they were live. Now a failed build sends a push notification to my phone, and a health report checks production every 30 minutes. The lesson: monitor the pipeline itself, not only the apps it deploys.
  • Probes are not optional. Before every service had proper startup, readiness and liveness probes, a slow start could be marked healthy too early and drop requests during a rollout. Adding them to all services ended a whole class of "it worked after a minute" bugs.
  • Fewer services is a feature. I started with too many small services. Merging several of them (users into auth, notifications into real-time) removed pipelines, repos and failure points without removing a single feature.

What I would change next

  • A staging step. Today every merge goes straight to production. The next step is an automatic deploy to a staging overlay, a smoke test, then promotion to production by a second commit.
  • Webhooks instead of polling. Jenkins checks for new commits every few minutes. A webhook would cut that delay to seconds.
  • Tests that mean more. Some services still have thin test suites. The pipeline is only as safe as the checks it runs.
The takeaway. As a solo developer, the goal is not a clever pipeline. It is one path, the same for every service, where every deploy is a commit and every rollback is a revert. That is what lets one person run twenty apps and still sleep.
